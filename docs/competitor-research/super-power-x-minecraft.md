# Super Power X Minecraft 竞品技术拆解

调研日期：2026-08-28
竞品页面：[Astrocade · Super Power X Minecraft](https://www.astrocade.com/games/super-power-x-minecraft/01KYSV030HA9ZP3TTHH47WHDXR)

> 本文只记录可观察到的技术结构与玩法设计，用于 clean-room 实现；不复制竞品源码、素材或商标内容。

## 结论先行

竞品不是一个“Minecraft 风格场景”，而是一套完整的浏览器体素沙盒。当前 Operone 的 `VoxelFrontierScene` 只是约 300 行的 Phaser 伪透视任务场景，缺少体素引擎、连续世界和沙盒系统，不能靠补 UI、贴图或几个按钮追平。

第一款必须重做为独立、可复用的 WebGL voxel runtime。它仍可接入 Operone 的项目、音频、结算和埋点接口，但不能继续塞在 Phaser 2D 场景里。

## Astrocade 为什么能生产出高质量游戏

前面的成品技术拆解只能说明“这款游戏是什么”，不能单独解释“平台怎样把它生产出来”。结合 Astrocade 官方披露、真实创建页面和成品 iframe，可以还原出以下生产闭环。

### 1. AstroBrain 不是写代码模型，而是总制片/总编排

Astrocade 官方称其专有模型 AstroBrain 会统筹其它模型，处理把创意变为成品所需的细节。2.0 之后又明确说明，后台不是一个 AI，而是一组专门 Agent：分别负责视觉、UI、玩法和 game feel，再由编排层协作。

合理的工程推断是：用户提示不会直接进入一次性代码生成，而会先被拆成游戏设计、机制、资产、界面、声音、技术依赖和验收任务，再由不同生产器生成并汇总。官方没有公开具体模型名称、提示词或调度算法，因此这部分不能假装已经知道。

### 2. 首稿只是起点，质量来自多轮对话修改

真实创建入口首先用 AI 做灵感引导和概念细化。官方创作者案例明确说，泛化提示先得到约 80% 的基础版本，之后会围绕截图和具体问题反复修改；官方教程也直接提醒：如果停在第一次 wish，结果可能粗糙或未完成。

典型迭代不是“再生成一次整个游戏”，而是小步修正：

- 背景与相机视角是否一致。
- 角色、场景和道具比例。
- 移动方向、镜像与滚动同步。
- 阴影、层级、命中框。
- 攻击、受伤、生成、拾取等事件反馈。
- 动画尺寸、帧率和透视一致性。

所以高质量作品通常不是一次生成结果，而是创作者与 Agent 多轮共同打磨的版本。

### 3. 每款游戏都有 AI 生成的专属编辑器

Astrocade 2.0 官方说明，每款游戏的 edit mode 都会根据该游戏部分生成。成品 iframe 中也能看到平台注入的 `editMenu`、参数 onChange、复制/删除、批量操作和 commit checkpoint 接口。

这意味着它没有把所有游戏压进固定模板面板，而是允许游戏代码声明自己的可编辑对象和参数，再由平台生成适配当前作品的编辑体验。复杂游戏可以暴露世界 seed、渲染距离、生物开关、移动速度等专属参数，简单游戏则显示另一套控件。

### 4. 代码、资产和平台能力分层生产

成品中存在清晰分层：

- 游戏本体代码：当前样本约 1.128 MB 文本代码。
- 游戏专属多语言资源。
- Asset Map：图片、音频、3D 模型及其生成提示和元数据。
- 平台注入库：手势、错误、资源加载、排行榜、用户状态、编辑器回调、遥测。
- 安全 iframe：允许脚本和 pointer lock，但隔离作品代码。

因此高质量不是靠一个通用 Phaser 场景换参数，而是让每款作品拥有独立代码和独立资产，同时复用成熟的平台桥接层。

### 5. 专门资产模型提供统一生产资料

官方称其使用一套专门模型生成景观、角色和动画，并以自有受偿艺术家、动画师的原创作品进行微调。当前样本的 Asset Map 包含 137 个资源，并保存每项资产的 prompt、类型、用途、比例、压缩建议与缩放信息。

资产不是生成完一张图就结束，而是带语义进入运行时：地面贴图要求无缝平铺，角色模型走 GLTF/DRACO，音效按事件绑定，图标和世界贴图有不同压缩/缩放策略。资产元数据让代码 Agent 知道如何正确使用，而不是盲猜图片用途。

### 6. 运行时基础设施消化通用难题

平台提前提供错误处理、手势检测、资产加载、动画播放、存档、排行榜、多人房间、编辑状态 checkpoint 等通用能力。游戏生成 Agent 因此可以把精力集中在作品逻辑，而不是每次重新实现登录、上传、排行榜和移动端判断。

这也是成品代码虽然独立，却仍能快速接入 Astrocade 产品生态的原因。

### 7. 质量门槛来自真实玩家数据，而非生成完成状态

新发布游戏会立刻被分发给一小批随机玩家冷启动测试。平台持续观察总游玩、30 秒以上的 significant plays、中位游玩时长和 0–10 秒、10–30 秒、30–60 秒、2–5 分钟、10 分钟以上的流失区间。表现差的游戏在一两天内可能被降低分发甚至下架。

这会迫使创作者优化：

- 5–10 秒内到达第一个乐趣点。
- 降低下载和首屏加载时间。
- 避免长教程和不清楚的控制。
- 修复低帧率与输入延迟。
- 建立难度、进度、内容和视觉变化。

高质量是生成、真实分发、数据诊断、再次编辑的循环结果。

### 8. 自动 QA 来自海量真实操作—状态数据

官方称每次点击、滑动、跳跃、合成、得分、死亡和重试都会记录成结构化的动作—环境状态转移，并已积累数以百万计的真人游玩会话。这些数据被用于训练能够探索新游戏的 QA Agent：测试移动、边界、胜负条件和失败状态，找出损坏机制。

这比按固定坐标点击几次更强，因为 Agent 学的是“动作怎样改变游戏世界”，而不是只判断某个 DOM 或状态字段存在。

### 9. 人的游戏设计能力仍然参与闭环

Astrocade 自己承认降低工程门槛并不保证游戏好玩，因此通过 Astro Academy 和团队 Office Hours 教创作者：降低 time-to-fun、控制下载、设计进度、补 game juice、先打磨核心机制再向外扩展，并持续找真人试玩。

因此正确结论不是“它有更强的一个模型”，而是：

**多 Agent 制作系统 + 独立代码/资产生成 + 专属编辑器 + 多轮创作者迭代 + 平台运行时 + 自动 QA + 真人流量与留存反馈，共同把少量好作品筛选和打磨出来。**

## 竞品如何承载游戏

- 外层是 Astrocade 的 Next.js 产品壳。
- 游戏被完整写入一个 `srcdoc` iframe，sandbox 为 `allow-scripts allow-pointer-lock`，隔离游戏代码，同时允许第一人称鼠标锁定。
- 设计基准是 `720 × 1280` 竖屏，再按容器比例缩放；桌面和移动端共享同一运行时。
- iframe 中可区分四层：
  - 约 3.2 KB 错误处理注入。
  - 约 9 KB 手势追踪注入。
  - 约 165 KB Astrocade 游戏平台库，负责资产、状态、排行榜、用户存档和编辑能力桥接。
  - 约 12 KB 多语言资源与约 1.128 MB 游戏本体代码。

这说明竞品平台的关键能力不是“给每款游戏套一个统一小游戏模板”，而是为独立游戏代码提供稳定的 iframe 沙箱和平台桥接。

## 渲染与世界技术

### 引擎与依赖

- Three.js r128：`WebGLRenderer`、`PerspectiveCamera`、`Raycaster`、`InstancedMesh`、`BoxGeometry`。
- Three.js GLTFLoader、DRACOLoader、SkeletonUtils：加载和复用角色/生物模型。
- PeerJS + Firebase Realtime Database：房间、玩家和世界修改同步。

### 世界数据

- X/Z 方向按需生成，配置声明为无限；世界高度 64。
- 区块为 `16 × 16 × 16`。
- 默认预构建半径 128，避免出生点边走边卡。
- 地形基于确定性种子和多层平滑噪声，叠加平原、山地、洞穴、树木、花、村庄与稀有方块规则。
- 修改过的方块单独持久化，基础地形可由 seed 重建。

### 性能策略

- 同类方块使用 `InstancedMesh`，单类型最多 50,000 个实例。
- 近区块使用 exposed-face 检查与 greedy meshing，合并相邻同类方块。
- LOD 距离为近 40、中 80、远 160；远景使用简化网格。
- 使用视锥裁剪、射线裁剪、chunk dirty 标记、对象池和分帧重建。
- 地形列缓存上限 10,000；可见区刷新有位移阈值和 250ms 节流。
- 移动端点光源上限 6，桌面上限 50；生物可见数量也单独限流。

这套组合解决的是“世界大、方块多、仍能在手机浏览器跑”的问题。逐方块创建普通 Mesh 会很快失控。

## 玩家交互不是按钮任务

### 第一人称控制

- 真实透视摄像机、鼠标 pointer lock、WASD、跳跃、重力、落地和方块碰撞。
- 移动端有独立移动摇杆与视角触控区，不是四个离散方向按钮。
- 支持第一/第三人称切换、本地角色模型、手臂挥动和动作反馈。

### 挖掘与放置

- 使用 3D DDA voxel traversal 找准星方向上的首个实体方块，而不是估算“玩家前方两格”。
- 不同方块有硬度；工具只对适配方块提供挖掘倍率。
- 持续按住才累计挖掘进度，并有进度条、声音和手臂动画。
- 放置会根据命中面确定目标格，并检查玩家占位、特殊方块朝向和库存。
- 水与岩浆有源方块/流动方块传播，TNT 有倒计时和范围破坏。

### 生存与成长

- 生命、饥饿、受伤、跌落伤害、昼夜循环（默认 180 秒）。
- 完整背包、9 格快捷栏、物品移动、合成区、配方书与自动合成。
- 创造模式、暂停、保存、读取、导出 JSON、导入 JSON、删除存档。
- 本次实玩确认背包不是装饰：界面列出合成配方、主背包和快捷栏，并可移动物品。

## 内容规模

- 39 个独立方块类：基础地形、矿石、木材、玻璃、门、床、箱子、熔炉、火把、水/岩浆、耕地、植物、铁轨、矿车、幸运方块等。
- 15 个生物类：Zombie、Creeper、Skeleton、Spider、Villager、Cow、Sheep、Dog、Panda、Parrot、Enderman、Slime 等。
- 9 个超能力：激光眼、雷击、火球、冰冻、超级跳跃、超级速度、飞行、力场盾、瞬移冲刺；各自有冷却、音效、粒子/光照和命中逻辑。
- 137 个外部资源：102 张图片、28 段音频、7 个 3D 模型。
- 联机同步覆盖方块修改、玩家位置/动作、聊天、生物、矿车和世界房间。

## Operone 当前版本的根本差距

| 维度 | 竞品 | 当前 VoxelFrontier |
|---|---|---|
| 空间 | 真实 WebGL 3D 世界 | Phaser Graphics 伪透视投影 |
| 世界 | Seed + chunk 按需生成 | 13 × 13 二维高度数组 |
| 渲染 | Instancing + greedy mesh + LOD | 每帧重画多边形 |
| 交互 | DDA 射线、硬度、工具、连续挖掘 | 估算前方格，按键立即减高度 |
| 运动 | 重力、跳跃、碰撞、第一/三人称 | 平面坐标移动，无实体碰撞 |
| 系统 | 背包、合成、生存、昼夜、流体、存档 | 方块/晶核两个计数器 |
| 内容 | 39 方块、15 生物、9 能力 | 3 个晶核点，无真正生物 |
| 资源 | 137 个图像/音频/模型资产 | 纯色几何与文字 HUD |
| 联机 | Firebase + PeerJS 房间同步 | 无 |

因此，原来的“脚本完成 3 次挖掘 + 4 次放置”只能证明状态变量会变化，不能证明它是一款沙盒游戏。

## 建议的 clean-room 重做边界

### 第一阶段：可玩的体素地基（必须一次做对）

- 新增独立 Three.js TypeScript runtime，与 Phaser runtime 并列。
- `16³` chunk、确定性 seed、按需加载、dirty chunk 重建。
- greedy meshing 或面级实例化；不能每个方块一个普通 Mesh。
- 真实第一人称摄像机、重力、跳跃、台阶和 AABB 碰撞。
- 3D DDA 挖掘/放置、命中描边、连续挖掘进度。
- 桌面 pointer lock + 移动端双摇杆。
- 至少 8 种方块、快捷栏、背包与本地存档。

### 第二阶段：形成十分钟玩法循环

- 木材 → 木板 → 工作台 → 镐子的真实合成链。
- 石材和矿石分层，工具影响开采效率。
- 生命、饥饿、昼夜、跌落伤害。
- 至少 3 种生物：被动、近战敌对、远程敌对各一种。
- 5 个差异明确的超能力，并有冷却、命中和视听反馈。
- 建造、战斗、采集和探索能够互相供给，而不是独立按钮。

### 第三阶段：内容和平台化

- 扩到 20+ 方块、6+ 生物、9 个能力。
- 箱子、熔炉、耕作、流体、TNT、村庄等系统按优先级加入。
- 把 voxel runtime 作为平台可生成/可配置的正式运行时，而非只为一个样品硬编码。
- 联机放到单机纵切稳定之后；优先保证世界状态和存档模型能支持未来同步。

## 验收标准

不能再以“QA 状态字段达到目标值”为主要验收。第一阶段至少要同时满足：

1. 新玩家不看说明，也能在 30 秒内移动、转头并成功挖掉一个方块。
2. 连续玩 10 分钟可完成采集、合成、建造、战斗、使用能力五种不同动作。
3. 退出重进后，玩家位置、背包和修改过的方块仍在。
4. 桌面端 pointer lock 与移动端双摇杆都完成真实操作验收。
5. 中端手机视口下没有持续性卡顿；chunk 重建不造成明显长帧。
6. 自动化只验证确定性规则；最终必须保留真实浏览器手玩记录和画面对比。

## 产品决策

第一款的正确目标不是“外观接近竞品截图”，而是做出一个较小但完整的体素沙盒纵切。若资源不足，应减少方块、生物和能力数量，但不能删掉真实 3D 世界、碰撞、DDA 交互、背包/合成和存档这些骨架。
